# 設計

ML-Quest の今の設計と決まりをまとめる. まだやっていないことは [TODO.md](../TODO.md) にある.

## 1. 役割と位置づけ

「機械学習を全て GUI 上で行う」アプリ (問題の設定, データの分析, モデルの作成・選定, モデルの学習・評価, 推論の段階に分けて作ることを目指している) のうち, 「問題の設定」の段階でライブラリを受け持つ. 画面は ML-Pathfinder.

機械学習は課題を解く手段の 1 つにすぎない. 推論や学習がゴールになるのを防ぐため, 課題から始めて, 課題を分解し, どの部分を機械学習に任せると課題の解決につながるかの筋道を, 1 つのファイル (問題の設定) に残す. 後ろの段階 (データの分析, モデルの作成, 学習・評価, 推論) が要る値 (目的の列, タスク, 使ってよい列, 評価の指標, 意思決定の損得と制約) は, 全てこの筋道から出る.

- **問い**: 問題の設定を決まった順の問いで埋める. 問いの並びと中身はこのライブラリが持ち, 画面 (ML-Pathfinder) はそれを順に出すだけ
- **確かめ**: 答えどうしの食い違い (量を決めるのに分類のタスク, 予測の時点で分からない列を使う, など) と, 足りない答えを一覧にする
- **受け渡し**: 後ろの段階ごとに, 問題の設定から決まる値をまとめて返す
- **骨組み**: 問題の設定から, 学習・評価の段階 (ML-Found) のプロジェクトの骨組み (config と学習のスクリプト) を書き出す
- **機械学習を使わない出口**: 課題の分解の結果, 機械学習が要らない (ルールや集計, 今のやり方の改善で足りる) と分かれば, そこで終えられる. 問題の設定は機械学習の入口ではなく, 機械学習が要るかを決める場所
- **他の段階との分け方**: 後ろの段階は, 問題の設定のファイルをこのライブラリを通して読む (YAML を自分で解釈しない). 段階どうしをつなぐかは, 要ると分かった所から段階ごとに決める (今は, データの分析の ML-Fathom は「問題の設定から始める」と書き戻し, 推論の ML-Provide は一式に問題の設定をつないで損得を読む. 他の段階は利用者が受け渡しの値を見て画面で選ぶ)
- 依存は軽くする (PyYAML と pandas. pandas はデータのファイルから列の名前を読むためだけ). 前処理や学習はしない. 手元のデータから答えの候補を出す部分 (下の「データからの候補」) だけは ML-EDA を使う (任意の依存 `ml-quest[data]`. データの読み方は ML-EDA が持つ約束なので, 写して作り直さない)

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| 問題の設定 (problem) | 課題から, 決めること (行動), 機械学習の受け持ち, 損得, 確かめ方, 運用までを決めたもの. `problem.yaml` |
| 受け持ち (part) | 課題から見た, 機械学習の最後の出力の役 (予測する, 作る, 並べる, まとめる, 効果を見積もる) と, それに続く答え. `ml.parts` の 1 つ |
| 問い (question) | 問題の設定の 1 つの項目を埋めるための問い. 識別子は項目の場所 (`issue.pain` など) |
| 確かめ (finding) | 答えの食い違いや足りなさ. 重さは `error` (後ろの段階に渡せない), `warning` (渡せるが見直したい), `info` (知らせ) |
| 受け渡し (handoff) | 後ろの段階ごとの, 問題の設定から決まる値 |
| 骨組み (skeleton) | ML-Found のプロジェクトの形の, config と学習のスクリプトの雛形 |

## 5. 問題の設定の形 (版 2)

```yaml
format_version: 2
name: 総菜の作る量                 # 問題の名前
created_at: "2026-11-17T21:30:00+09:00"
updated_at: "2026-11-17T21:45:00+09:00"

issue:                            # 1. 課題
  owner: 店長                     #    誰の課題か
  pain: 総菜の廃棄が多く, 夕方には品切れも出る
  current: 前の週の同じ曜日と同じ数を作る   # 今のやり方
  kpi:                            # 2. 解けたと言える指標
    name: 廃棄と欠品の損
    unit: 円 / 月
    current: 1200000              #    今の値 (分かれば)
    target: 960000                #    目指す値
    better: lower                 #    lower (小さいほど良い) か higher
  guard:                          #    守る指標 (任意. 引き換えに悪くしてはいけない数字)
    name: 品切れした品と日の割合
    unit: "%"
    better: lower                 #    向き (名前を書いたら要る)
    line: 5                       #    守る線 (これを割ったら失敗. 名前を書いたら要る)
    measure: 閉店の 2 時間前に棚が空の品と日を数える

decomposition:                    # 3. 課題の分解 (要因と打てる手)
  - cause: 作る量が勘で決まる
    lever: 作る量を売れる数の予測から決める
    ml: true                      #    機械学習で手伝う手か
  - cause: 夕方の値引きが遅い
    lever: 値引きの時刻を決めておく
    ml: false

ml:                               # 5. 機械学習の受け持ち
  use: true                       #    false なら機械学習を使わない (reason に理由)
  reason: 品と日による売れ方の違いが大きく, 今のやり方では追えない
  constraints: []                 # 7. 機械学習の仕組みが守る制約 (任意. 文の並び)
  parts:                          #    受け持ちの並び (今は 1 つだけ書ける)
    - role: predict               #    受け持ち (下の表)
      unit: row                   #    1 件の単位
      output: value               #    出力の形
      target:                     #    正解
        source: column            #      正解の出どころ
        process: null             #      今の処理の出力なら, その処理 (name, settings)
        kind: column              #      正解の種類 (予測すると作るで問う)
        column: sales             #      目的の列 (正解の種類が column のとき)
      method: scratch             #    作り方
      what: 翌日の品ごとの売れる数   #    何を出すか (文)
      item: 店, 品, 日ごとの 1 行   #    1 件は何か (文)
      task: forecasting           #    列の正解の種類 (classification, regression, forecasting)
      positive: null              #    2 クラスの分類で当たりのクラス
      group_column: null          #    同じ相手の行をまとめる列 (任意. 分割をまたがせない)
      split_time_column: null     #    分類と回帰を時刻の順で分けて確かめるときの時刻の列 (任意)
      time_column: date           #    時刻の列 (forecasting では必須)
      series_by: [store, item]    #    系列を分ける列
      available_lag: 2            #    決める時点で目的の値は何期前の分まで分かるか (forecasting で必須)
      horizon: 1                  #    何期先まで予測するか (forecasting で必須)
      baseline: 前の週の同じ曜日と同じ数   # 機械学習を使わない比べる相手
      consumer: rule              #    出力の使い道 (任意. human, rule, system, model, deliver)
      downstream: null            #    後段が求める形と精度 (system と model のとき)
      evaluation:                 # 8. 最良のモデルを選ぶ指標
        metric: mae               #    受け持ちと正解の種類ごとの候補か other
        name: null                #    other のときの名前 (監視する指標 valid/<名前>)
        better: null              #    other のときの向き (lower か higher)
        link: 誤差が小さいほど作る量の外れが減り, 廃棄と欠品の損が減る
        current: null             #    今のやり方でのこの指標の値 (画像と文, 画像の領域と点群. 分かれば)

data:                             # 5. 手元のデータ (任意. ML-EDA の読み方)
  source: /data/sozai.csv         #    データの場所 (絶対パス. 写したなら写しの場所で, origin に元の場所)
  loader: csv                     #    ML-EDA の読み込みの種類と設定 (Data.source と同じ)
  options: {time_column: date}
  missing: [天気予報の記録]        # 6. 要るのに手元に無いデータ

information:                      # 6. 予測の時点で使える情報 (columns は 5 で問う)
  columns: [date, store, item, sales, temperature_forecast, promo, customers]
  known: [store, item, temperature_forecast, promo]   # 予測の時点で分かる列
  unknown: [customers]            #    分からない列 (学習に使わない)
  forbidden: []                   #    分かっていても使ってはいけない列 (ID, 個人の情報など)

action:                           # 4. 決めること (機械学習を使うかに関わらず問う)
  who: 店長
  when: 前の日の 17 時
  what: 品ごとの作る量
  decision:                       # 7. 損得と制約 (ML-Inference の decision の形)
    type: quantity
    under_cost: 200
    over_cost: 150
  basis: 欠品は粗利 200 円, 廃棄は原価 150 円   # 損得の値の根拠

verification:                     # 9. 効果の確かめ方
  method: both                    #    backtest (過去のデータでたどり直す), trial (実際に試す), both
  backtest: 過去 3 か月で, 今のやり方と損を比べる
  trial: 1 店で 4 週間
  success: 廃棄と欠品の損が今のやり方より 2 割少ない

operation:                        # 10. 運用
  review: 月に 1 回
  approver: 本部
  stop: 損が今のやり方より悪い月が 2 回続いたら止める
  remeasure: 月に 1 回, 前の月の実績で外れ方を確かめ, 本部が承認したら書き戻す

project:                          # 書き出した学習のプロジェクト (任意. record_project が書く)
  path: /work/sozai_project       #    プロジェクトのディレクトリ (絶対パス)
  dataset: /work/sozai_project/outputs/dataset      # train.py がデータセットを読む場所 (config の data.dataset)
  model_spec: /work/sozai_project/models/model.yaml # train.py がモデルの定義を読む場所 (config の model.spec. 無ければ null)

origin: /work/problems/sozai/problem.yaml # 元の問題の設定 (写しだけが持つ. make_project が書く. 絶対パス)
```

- 上から順に決める. 各項目は次の項目の根拠になる (課題が無ければ指標は決まらず, 指標が無ければ機械学習の受け持ちの良し悪しは決まらない)
- 番号は問いの順 (4 の決めることと 7 の損得は `action` に一緒に置く. 損得は行動の結果の値なので. そのためファイルでは `action` が後ろにある). ただし使えるデータの列 (`information.columns`) は, 目的の列を選ぶ前に要るので 5 で問う
- 何を決めるか (4) は, 機械学習に何を出させるか (5) より先に問う. 予測は決めるために使うもので, 予測を先に問うと「予測できそうなものを予測する」逆向きの考え方を誘うため. 機械学習を使わない場合も問う (決めることは課題を解くために要る. 4 の 3 つの問いが空なら, 機械学習を使わない問題の設定でも足りない答えの誤り)
- `ml.use` が `false` なら, 1 から 4 と, 使うかとその理由の他は要らない (機械学習を使わない出口. 代わりの手の確かめ方や運用は, このライブラリの対象外)
- 系列を分ける列と時刻の列も, 予測の時点で分かって学習に使うなら `known` に入れる (店や品のワンホットなど)
- 決める時点で分かる目的の値 (`available_lag`) は, 予測の時点で使える列と同じく漏れを防ぐための答え. 前の日の 17 時に翌日を決めるなら, 前の日の値はまだ確定しないので 2. 学習に 1 期前の値を使うと, 学習とたどり直しでは当たり, 使うときは外れる (ML_tester の 21 で, 1 期前からと 2 期前からで, たどり直しの今のやり方との差を比べられる)
- `action.decision` は ML-Inference の意思決定の形 (`type` は `quantity`, `select`, `triage`, `none`) と同じ. `none` は予測を見て人が決める場合 (意思決定の材料を作らない). 対象を選ぶ型は, 効果の渡し方 (`effect_kind`: `share` 防げる割合 (既定) か `uplift` 行動したとき − しないときの当たりの確率) と, `uplift` の向き (`effect_goal`: 当たりを減らしたいなら `reduce`, 増やしたいなら `raise`) も書ける. 効果のモデル (介入の記録から学ぶ) の見積もりを, 確率を二重に掛けずに渡すため
- 書き出したプロジェクトの記録 (`project`) は, 後ろの段階の画面がデータセットとモデルの定義の置き場を写さずに使うためのもの. 答えではないので問いと確かめには出ない. 無い場合と, 絶対パスの文字でない値は「記録が無い」として扱う. この項目を知らない読む側は無視するだけで, 他の答えの意味は変わらないので, 版 2 に含む
- 元の問題の設定の場所 (`origin`) は, 骨組みのプロジェクトと学習の実験に写した問題の設定が, 元のファイル (ML-Pathfinder の置き場の `problem.yaml` など) を指すためのもの. 推論の段階は写しの代わりに元を読み, 写した後に直した損得を使う (写しは書き出した時点の値のまま). `problem_origin(problem)` で読む. 無い場合と, 絶対パスの文字でない値は「元の場所が無い」(`None`) として扱う. ファイルがあるかは見ない (読む側が確かめ, 無ければ写しを使う). 答えではないので問いと確かめには出ない. 写しを元の問題の設定として取り込む側 (ML-Pathfinder の置き場への取り込みなど) は `origin` を外す (外さないと, 取り込んだものが別の元を指す写しに見え, そこから書き出した写しが取り込み元の古い問題の設定をたどるため). `make_project` に渡す元の場所は, YAML のファイルの名前でなければディレクトリとして中の `problem.yaml` を指す. この項目を知らない読む側は無視するだけなので, 版 2 に含む
- 知らない項目は残す (読む側は無視する). 版を上げるのは, 項目を消すか, 名前, 意味, 値の型を変える場合

### 受け持ちと, 型に依らない 5 つの問い

1 つのファイルに課題は 1 つ. 機械学習の受け持ちは並び (`ml.parts`) で持つが, 今は 1 つだけ書ける (2 つ以上は確かめの `error`). 守る指標, 確かめ方, 運用は課題に 1 つなので受け持ちの外に置く. 問いの識別子は項目の場所なので, 受け持ちの問いは `ml.parts.0.role` のように並びの番号を持つ (`get_value` と `answer` は並びの番号をたどる).

5 の節の頭で, 型に依らない 5 つの問いを問う. 型ごとに続く問いは `when` で分ける.

| 問い | 場所 | 値 |
| --- | --- | --- |
| 受け持ち | `role` | `predict` 予測する (正解が 1 つに決まるものを当てる. 構造のある出力と異常も), `generate` 作る (正解が 1 つに決まらない中身), `rank` 並べる (候補から要求に合うものを順に), `group` まとめる (正解の無いデータをまとまりに), `effect` 効果を見積もる (行動したときとしないときの差) |
| 1 件の単位 | `unit` | `row` 行, `bundle` まとまり (撮影, 文書と添付), `pair` 対 (入力と正解のファイル), `query` 要求と候補の組, `collection` 集まり (文書の束), `window` 時間の窓 |
| 出力の形 | `output` | `class` クラス, `value` 値, `distribution` 分布 (分位点, 区間), `region` 位置や領域, `shape` 3D の形, `text` 文, `image` 画像, `table` 表, `ranking` 順位, `cluster` 群, `effect` 行動ごとの差 (受け持ちに合うものだけを選択肢に出す) |
| 正解の出どころ | `target.source` | `column` データの列, `files` 対のファイル, `self` 自分自身 (隠して当てる, 元に戻す), `none` 無い, `few` 少し (確かめの組だけ), `process` 今の処理の出力, `objective` 目的の式, `feedback` 行動の結果, `intervention` 介入の記録, `human` 人の判断と好み, `instruction` 指示と例 |
| 作り方 | `method` | `rule` 規則, `pretrained` 既製のモデルをそのまま, `head` 既製の特徴の上に頭だけ学習, `partial` 一部を微調整, `finetune` 全体を微調整, `scratch` 一から学習 |

- 正解の出どころが今の処理の出力 (`process`) なら, その処理の名前 (`target.process.name`. 要る) と設定 (`target.process.settings`. 任意の文) を問う. 何で作ったかは問わないが, 評価と結論で「その処理を超えられない」ことを示せるように残す
- 正解の種類 (`target.kind`) は予測すると作るで問う: 予測するは `column` 表の列 (クラスか値), `mask` 画像の領域, `point_cloud` 点群, `text` 文. 作るは `text`, `image`, `table` 表 (合成のデータ), `point_cloud`
- 続く問い: 予測するで正解の種類が表の列のとき (以下「列の予測」) だけ, 版 1 の問い (タスク, 目的の列, 当たりのクラス, 時刻の列など), 使える列 (`information`), 意思決定の損得と今のやり方と根拠 (`action.decision`, `action.current`, `action.basis`) を問う. 並べる, まとめる, 効果を見積もるの受け持ちの中の問いは, 5 つの問いと何を出すか, 1 件は何か, 比べる相手, 使い道, 最良を選ぶ指標だけ (効果を見積もるは, 加えて方策かどうか, 行動の結果の集め方, 方策の守りも問う. 下の「続けて行動を選ぶ方策と守り」. 型ごとの通り道は TODO.md). 受け持ちに依らない問い (手元のデータ, 要るのに無いデータ, 制約, 9 と 10 の節) は全ての受け持ちで問う
- タスク (`task`) は列の正解の種類 (分類, 回帰, 時系列の予測) に限る. 型は受け持ち (`role`) と正解の種類 (`target.kind`) で表す

### 最良を選ぶ指標

学習の損失 (交差エントロピー, KL ダイバージェンスなど) は問わない. モデルの作成と学習の段階で決める. 問うのは, 検証用の分割で最も良いモデルを選ぶ指標 (`evaluation.metric`). 候補は受け持ち, 正解の種類, タスクごと.

| 受け持ちと正解の種類 | 候補 (向き) |
| --- | --- |
| 予測する, 表の列, 分類 | `accuracy` (大きい), `loss` 交差エントロピー (小さい) |
| 予測する, 表の列, 回帰と時系列の予測 | `mae` (小さい), `rmse` (小さい) |
| 予測する, 画像の領域 | `iou` (大きい), `loss` (小さい) |
| 予測する, 点群 | `chamfer` (小さい), `loss` (小さい) |
| 予測する, 文 | `cer` 文字の誤り率 (小さい), `loss` (小さい) |
| 作る | `loss` (小さい). 画像は `fid` (小さい) も |
| 並べる | `recall_at_k` (大きい), `ndcg` (大きい), `loss` (小さい) |
| まとめる | `silhouette` (大きい), `loss` (小さい) |
| 効果を見積もる | `qini` (大きい), `loss` (小さい) |
| 全て | `other` その他 (名前 `evaluation.name` と向き `evaluation.better` を書く) |

- 監視する指標は `valid/<指標>` (RMSE は並びの同じ `valid/mse`). その他は `valid/<名前>`. 名前は英数字と `_`, `.`, `@`, `-` だけ (`.` と `..` は除く. 学習の記録の名前と曲線のファイルの名前になるため)
- `loss` は `METRICS` に 2 つある (分類の交差エントロピーと, 他の受け持ちの損失. 監視する名前が同じ `valid/loss` なので値も同じ). 画面は `METRICS` を直接使わず, `questions` の `choices` (今の答えで絞り, 同じ値は 1 つ) を使う
- 指標をその他から変えた後の名前と向きは, 他の要らなくなった問いの古い答えと同じく, ファイルに残すが使わない (受け渡しは要る問いの答えだけを読む)
- 列の予測の出力の形は `class`, `value`, `distribution` のどれか (他は `error`)
- **今のやり方での指標の値** (`ml.parts.0.evaluation.current`. 任意の数. 問いは「今のやり方 (人の目視や今の仕組み) で, この指標は幾つですか (分かれば)」. `questions` は「この指標」を最良を選ぶ指標の名前 (正解率, IoU など. `METRIC_TITLES`) に置き換えて返す. 説明は例と「割合は 0 から 1, 誤差は目的の値 (点群は座標) の単位」までにし, 細かい数え方は README と評価の表の説明に書く): 骨組みが今のやり方の結果を 1 件ずつ並べられない受け持ち (入れたデータが画像か文の列の予測と, 画像の領域と点群) で, 最良を選ぶ指標が `accuracy`, `mae`, `rmse`, `iou`, `chamfer` のときに問う. 骨組みはこれを比べる相手にし, テスト用の分割のモデルの値と並べる (11 節の「今のやり方との比べ」). 数え方はモデルの値と同じにするよう, README と評価の表の説明に指標ごとの数え方と単位を書く (`REPORTED_METRICS`): 正解率と IoU は 0 から 1 の割合 (IoU はクラスごとの重なりの画素数を和の画素数で割り, 背景を除くクラスで平均. 予測にも正解にも無いクラスは 1), 平均絶対誤差と二乗平均平方根誤差は目的の値の単位, Chamfer 距離は最も近い点までの距離 (2 乗しない) を両向きで平均した和の半分で, データセットの座標の単位. 課題の指標の今の値 (`issue.kpi.current`) は事業の指標 (円など) で, 学習の指標と単位が違うことが多いので, 別に問う. 表と時系列は今のやり方をデータで書き (`action.current`), 同じ行で比べるので問わない. `loss` は今のやり方で数えられないので問わない
- 版 1 のファイルの指標は 4 つ (`accuracy`, `loss`, `mae`, `rmse`) のまま読め, 版 1 のファイルにそれ以外 (`other` も) を書くと「知らない指標」の誤り. 版 2 から候補と `other` を書ける. 版 1 の 4 つの他の指標は移さず, 版 1 の場所 (`evaluation.metric`) に残す (確かめで「知らない指標」. 最良を選ぶ指標に答えると消える)

### 続けて行動を選ぶ方策と守り

効果を見積もるの受け持ちで, 機械学習が観測を見て次の行動を続けて自分で選ぶ (方策. 機械の動かし方など) 場合は, 守りを問う (方策を作り, 確かめ, 守りと一緒に書き出すところまでを扱い, 実機での実行は道具の外. 人が決めるのは 1 回 1 回の行動ではなく, 方策を使ってよいかと守りの範囲).

```yaml
ml:
  gpu: true                         # GPU (CUDA) が要るか (任意. 全ての受け持ち)
  parts:
    - role: effect
      autonomous: true              # 続けて自分で行動を選ぶか (任意. 効果を見積もるだけ)
      collect: simulator            # 行動の結果の集め方 (任意. log 今ある記録, online 実際に試す, simulator)
      simulator: mujoco             # シミュレータ (collect が simulator なら要る. mujoco か other)
      env_id: null                  # Gymnasium の環境の登録名 (任意. 方策で, collect が log でないとき)
      ros2: false                   # 機械を ROS2 で動かすか (任意. 方策だけ)
      policy:                       # 方策の守り (方策だけ)
        action_limits: 各関節の速さは毎秒 0.5 rad まで    # 行動の上限 (要る)
        stop: 腕の先が作業の範囲 (台の上 0 から 0.3 m) を出たら   # 止める条件 (要る)
        fallback: handover          # 外れたときの動き (要る. stop, handover, action)
        fallback_action: null       # action のときの行動 (任意. 文)
        safety_key: cost            # 安全の違反の信号の名前 (任意)
        approver: 設備の責任者       # 方策を使ってよいかと守りの範囲を誰が決めるか (要る)
```

- 方策かどうか (`autonomous`) と集め方 (`collect`) は任意の問い. 答えなくても足りない答えの誤りにならない. 方策と答えたときだけ, 守りの問いが要る
- 守りの問いは, ML-Found の方策の守り (`make_guards`) に合わせる: 行動の上限は `action_low`, `action_high` か `allowed_actions`, 止める条件は観測の範囲 (`observation_low`, `observation_high`), 外れたときの動きは `fallback` (`stop` 止める, `handover` 元の制御に戻す, `action` 決めた行動. 名前は ML-Found と同じ), 安全の違反の信号は学習と評価の `safety_key` (空なら ML-Found の既定と同じ `cost` を受け渡す. `None` を渡すと ML-Found は違反を数えないため). 決めた行動 (`fallback_action`) は文, 数か数の並び (番号で選ぶ行動はその番号. 番号で選ぶ行動では ML-Found で要る. 量で決める行動は空なら 0 の行動). 問題の設定の時点では観測と行動の空間 (要素の並び) が決まっていないので, 行動の上限と止める条件は数の並びでなく文で書き, 学習の段階で空間が決まってから数にする
- **環境の登録名** (`env_id`. 任意の文): 方策で, 集め方が今ある記録 (`log`) でないとき (答えていない場合も) に問う. 答えると, 骨組みの学習のスクリプトが ML-Found の `make_env` でその環境を作る. 空なら自作の環境 (実機とのつなぎ, 自作のシミュレータ) として, 骨組みに環境の雛形を書き出す. 今ある記録からは環境とやり取りしないので問わない. 形は Gymnasium の登録名 (英数字と `_ . -`. 前に読み込むモジュールの `module:` と名前空間の `namespace/` は任意. 例 `CartPole-v1`, `ALE/Pong-v5`). 形が違えば確かめの `error` (骨組みを組めない. 学習のスクリプトに書くため). 登録されているかは見ない (Gymnasium に頼らないため. 学習の段階の `make_env` が確かめる). MuJoCo の環境 (`Hopper-v5` など) もシミュレータの答えとは別にここで答える
- 止める条件は 10 の節の「どうなったら止めますか」(方策を使うのをやめる条件) とは別で, 1 歩ごとに方策の出力を止める条件
- 承認する人は 10 の節で問う (「変更は誰が承認しますか」とは別. 方策を使ってよいかと守りの範囲)
- 受け渡しの `policy` (下の「受け渡し」) で, 学習・評価と推論の段階に渡す
- これらの項目は, 任意の問いか, 任意の問いに答えたときだけ要る問いなので, 版 2 に含む (版を上げるのは項目を消すか, 名前, 意味, 値の型を変える場合). これらを知らない ML-Quest は知らない項目として残す

### 要る機能

pip で入らないものを含む外の道具 (ROS2, MuJoCo, CUDA) は, 要るまで入れない. 問題の設定から要る機能を出し, 画面が早めに入れ方のカードを出せるようにする. 足りないかの確かめと入れ方は ML-Found の登録簿 (`describe_requirements`) が持ち, ML-Quest は名前だけを持つ (ML-Found に依存しない).

| 機能 (`FEATURES`) | 要る場合 |
| --- | --- |
| `rl` | 効果を見積もるで, 行動の結果を試して集める (`collect` が `online` か `simulator`) |
| `mujoco` | シミュレータに MuJoCo を選んだ (`simulator` が `mujoco`) |
| `ros2` | 方策で, 機械を ROS2 で動かす (`ros2` が `true`) |
| `cuda` | GPU (CUDA) が要る (`ml.gpu` が `true`) |

- `required_features(problem)` は, 答えから要る機能の名前を `FEATURES` の順で返す (要らなくなった問いの古い答えは使わない). 答えの途中でも呼べる (確かめに誤りがあっても返す. 画面がカードを早く出すため). 受け渡しの `requires` も同じ値
- 名前は ML-Found の登録簿の名前と同じにする. テストで, ML-Found が入っていれば全ての名前が登録簿にあるかを確かめる (入っていなければ飛ばす)
- GPU の問いは 7 の節 (制約) で全ての受け持ちに問う. 分からなければ空のまま (学習の段階で決める)

### 版と, 版 1 から移す

- 版 1 は「1 件の値を表の列から予測する」課題だけを書ける形 (`ml` の直下にタスクや目的の列, 学習の指標は `evaluation`). 版 2 は受け持ちごとの項目を `ml.parts` に持つ
- `upgrade_problem(problem)` は版 1 を版 2 に移す (元は変えない. 版 1 に手で書いた受け持ちがあれば, その答えは上書きしない. 受け持ちの並びが崩れていれば移さず, 確かめで形の誤り). 版 1 の値は全て移る: `ml.predict` → `what`, `ml.row` → `item`, `ml.target` → `target.column`, `ml.task`, `ml.positive`, `ml.group_column`, `ml.split_time_column`, `ml.time_column`, `ml.series_by`, `ml.available_lag`, `ml.horizon`, `ml.baseline`, `ml.consumer`, `ml.downstream` は同じ名前で受け持ちの中へ, `evaluation.metric` と `evaluation.link` は受け持ちの `evaluation` へ. `ml.use`, `ml.reason`, `ml.constraints` と他の節はそのまま. 知らない項目もそのまま残す
- 版 1 が前提にしていた答えは, 移すときに埋める: 受け持ちは `predict`, 1 件の単位は `row`, 正解の出どころと種類は `column`, 作り方は `scratch` (版 1 で書ける課題は, 表の列を一から学習するものだけのため), 出力の形はタスクから (分類は `class`, 他は `value`). 受け持ちを作るのは, 機械学習を使うか, 受け持ちの項目が 1 つでもある場合だけ
- **先に移す**: 問い, 答え, 確かめ, 受け渡し, 要約, 書き戻し, データの候補, 骨組みは, 版 1 の問題の設定を受け取ると先に版 2 に移して扱う (返す問題の設定は版 2). 版ごとに 2 通りの確かめを持たないため. `load_problem` も読んだ後に移す (ファイルは書くまで版 1 のまま)
- 版 1 の場所の名前 (`ml.target`, `ml.task`, `evaluation.metric` など) は, 版 2 の問題の設定でも `get_value`, `active_value`, `answer` で使える (移した先を読み書きする). 後ろの段階が版 1 の名前で読んでいても壊れないように
- 版が 1 以上の整数でない問題の設定 (文字列, 小数, 真偽値, 0) も, 読み込みと同じく誤り
- 知っている版より新しい版は読まない. `load_problem` と, 問題の設定を受け取る関数は誤り (`ValueError`) で止まり, `check` は版の誤りだけを返す (読める項目だけを使うと, 黙って読み違えるため)

## 6. 問い

`questions(problem)` は, 問いの並びを, 今の答えと, 答えたか, 今は要らないか (`ml.use` が `false` の場合の `ml.target` など) と一緒に返す. 画面はこれを上から順に出す.

| 問いの種類 (`kind`) | 答えの形 |
| --- | --- |
| `text` | 文 |
| `number` | 数 |
| `choice` | 決まった選択肢の 1 つ (`choices` に値と説明. 今の答え (受け持ち, 正解の種類, タスク) に合うものだけ) |
| `boolean` | はいかいいえ |
| `column` | データの列の名前の 1 つ (`information.columns` から) |
| `columns` | データの列の名前の並び |
| `list` | 文の並び |
| `levers` | 要因と打てる手の並び (`decomposition`) |
| `decision` | 意思決定の型と損得と制約 (ML-Inference の形). `choices` は型ごとに名前と欄 (`fields`: `key`, `label`, `required`, 選んで書く欄は `choices` と選ばないときの意味 `unset`, 他の欄の値で要るかが決まる欄は `when`) を持ち, 画面はこれだけで描く |
| `baseline` | 今のやり方をデータで書いたもの (`type` と `periods` か `column`. 下の「今のやり方をデータで書く」) |
| `source` | データの場所 (絶対パス. `~` は展開する). 画面はファイルを選ばせて `attach_data` で入れる (`answer` で場所だけを答えると, 読み方と列の名前は入らない) |

- 各問いは `id` (項目の場所), `section` (1 から 10), `title` (問い), `help` (なぜ問うか, 例), `required`, `kind` を持つ. `when` (条件の並び. 全てを満たすときに要る. 条件は, 項目の値が等しい `equals`, 並びに入る `in`, 答えたか `filled`, 中の条件のどれかを満たす `any` (例: データの読み込みが画像か文か, 正解の種類が画像の領域か点群か), 中の条件のどれも満たさない `none`) で, 今の答えのもとで要るかが決まる (機械学習を使う場合だけ, 受け持ちごと, 列の予測だけ, 分類だけ, 時系列の予測だけ, など)
- 要らなくなった問いの古い答え (タスクを回帰に変えた後の時刻の列など) は, ファイルには残すが, 確かめ, 受け渡し, 要約, 骨組みでは使わない
- `answer(problem, id, value)` は, 答えの形を確かめて問題の設定に入れ, 新しい問題の設定を返す (元は変えない). 形の誤りは `ValueError`. 空 (None や空の文字列) は答えを消し, 空になった親の項目も消す. 文の答えは, 行ごとに続く空白を 1 つにし, 改行は残す (続く空の行は 1 つに)
- 損得の値は数か列の名前. 数として読める文字列 (`1e3`, `+5`, 桁区切りの `1,200`) は数にし, 数に見えて読めない文字列 (`1,2,3`, `-`) と無限大, 非数は誤り. それ以外の文字列は行ごとの値の列の名前で, 使えるデータの列にあるかを確かめで見る
- 列の名前は, 利用者が選んだデータのファイルから `read_columns(path)` で読む (csv と tsv は 1 行目だけで, UTF-8 で読めなければ Shift_JIS. parquet は形の情報だけ (pyarrow が要る). Excel は openpyxl が要る). 同じ名前の列と空のファイルは誤り

## 7. データからの候補

課題, 指標, 分解, 決めること (1 から 4) はデータ無しで答える. 手元のデータから考え始めると, 技術の側から組み立てて「このデータで何が予測できるか」になりやすいため. データは 5 (機械学習の受け持ち) で入れ, 後の問いの答えの候補と確かめに使う. 手元のデータが課題に要るデータとは限らないので, 要るのに無いデータ (`data.missing`) も書ける (まずデータを集める, という結論もありうる).

- `attach_data(problem, path)` は, ML-EDA の `load_data` でデータを読み, 読めた種類と設定 (`Data.source` の `loader` と `options`. 時刻の列は除く), ファイルの大きさと更新の時刻, 場所を `data` に, 列の名前を `information.columns` に入れた新しい問題の設定を返す. 写し先 (`copy_to`) を渡さなければデータは写さない (写し方は下). 読み方の指定 (Excel のシートなど) は受け取らない
- 時刻の列は読み方に持たず, 読むたびに答え (`ml.time_column`) から付ける. まず ML-EDA の推定で読み (系列を分ける列も推定される), 推定した時刻の列が答えと違うときだけ, 答えた列を日時の列に指定して読み直す (店と品のように系列を分ける列が複数あると推定できないため). 答えた列がデータに無ければ指定せずに読み, 確かめで知らせる
- `inspect_data(problem)` は, 入れたデータを同じ読み方で読み直し, ML-EDA の `profile` (目的の列を答えていればそれとの関係も) から次を返す. 重いので `check` とは分け, 画面は必要なときに呼ぶ
    - 概要: 行の数, 列の数, 種類 (表か時系列), 時刻の範囲と間隔
    - 概要には, ML-EDA が大きなデータを見本の行で分析したか (`sampled`) も入れる (読み込みは全体)
    - 答えの候補 (問いの識別子ごとの値の並びと理由. 押せば答えになる値だけ): 目的の列 (答えたタスクに合う型. 回帰と予測は数, 分類は種類の少ない列. ID のような列, 定数の列, 時刻と系列の列は除く), タスク (まだ答えていなければ, 目的の列の型と時系列か), 当たりのクラス (分類の目的の列の全ての値), 時刻の列 (日時の列), 系列を分ける列 (数でない列のうち, 同じ時刻に複数の値が並び, 時刻と組にするとほとんど重ならない列), 使ってはいけない列 (ID のような列. `id_like`)
    - 確かめ (`check` と同じ形): データが少ない (100 未満. 表と時系列は行, 画像, 文, 点群, 撮影は 1 行が 1 件なので件で数える), 入れた後にファイルが変わった, 使えるデータの列とデータの列が違う, 答えた時刻の列や目的の列がデータに無い, 当たりのクラスがデータの値に無い (全ての値で. 1 と 1.0 は同じ), 分類で答える意思決定 (対象を選ぶ, 振り分ける) の目的の列の値が 2 種類でない (`error`. 推論の段階の ML-Inference はこれらの意思決定を 2 クラスの分類の一式にだけ使い, 学習を終えて一式を作るまで分からないため. 意思決定しない場合は推論の段階に渡らないので見ない. 他のデータの確かめの `error` と同じく, 骨組みは「それでも書き出す」と指定すれば (`accept_errors`) 書き出せる. 11 節の「残っている直すところ」. データを入れない場合は推論の一式を作るまで分からない), 答えたタスクと目的の列の型の食い違い (知らせ), 漏れの疑い (目的の列とほぼ同じ動きの列. ML-EDA の `target_leak`. 予測の時点で分かるなら使ってよいので, 値は入れさせず確かめてもらう), 何期先までがデータの期間に比べて長い (データの間隔で数えた目安), データが読めない. ML-EDA の気付きは問題の設定に関わるもの (目的の列の欠損, クラスの偏り, 多い欠損, 重複, 時刻の間隔) だけを重さのまま添える
- 受け渡しのデータの分析の値に, データの場所と読み方 (`source`) を入れる (全体のシステムでは ML-Fathom が同じ読み方で開く想定)
- **ファイルの組のデータセット (版 2 と版 3)**: ML-EDA が版 2 か版 3 (`dataset.yaml` の `format_version` が 2 か 3. 画像と領域の対, 撮影と点群の対. 版 3 は書き出しで中身の手順をかけ, 項目の `steps` に残したもの) で書き出したディレクトリも入れられる (ファイルの組の正解は表の列でないため, データの分析の段階で書き出したものをそのまま入れる). `attach_data` は `dataset.yaml` を持つディレクトリを ML-EDA の `load_items` で読めるかを確かめ, 読み方を `loader: items` にする (列の名前は入れず, 前の列の答えも変えない. ファイルの組の受け持ちは使えるデータの列を問わない). 写し方は他のデータと同じ. `inspect_data` は概要 (`overview`) を空にし, 版, 件数, 分割, 正解の種類と出どころ, 版 3 なら項目ごとの中身の手順 (`image: resize (width 64, height 64)` など) を `info` で, 受け持ちと正解の種類が問題の設定と違えば `error` で (`items_message`. 骨組みの書き出しと同じ決まり. 列の予測に入れた場合も, 列の予測には使えないと `error` で), 検証用の分割が無ければ `warning` で返す. 答えの候補は出さず, 入れた後にファイルが変わったかも見ない (書き出し直したら入れ直す). 版 1 のデータセット (`dataset.yaml` の版 1) は ML-EDA の読み込みに任せる. 版 2 と版 3 は同じに扱う (版 3 のファイルは手順をかけた後なので, 学習で読むのは版 2 と同じ. 手順は推論の段階が新しい 1 件にかける). 読める版の組 (`ITEMS_VERSIONS`) は ML-EDA の `ITEMS_FORMAT_VERSIONS` と同じ値を写して持つ (ML-EDA を入れなくても版を確かめられるように). それより新しい版は「この ML-Quest では読めません」で止める
- データは写して持つ. `attach_data(problem, path, copy_to=...)` は, 写し先を渡すとファイル (かディレクトリ) を写し, `data.source` を写した場所, `data.origin` を元の場所にする. 画面は問題の設定ごとの置き場に写す. `make_project` は, データを入れていればプロジェクトの `data/` に写し, プロジェクトの問題の設定の `data.source` をそこにする (学習のプロジェクトだけで, データの分析から学習までをやり直せるように). 写しも上書きの確かめの対象. 写し先が相対パスか元のディレクトリの中なら誤り. 元の場所は `..` などを正規化してから写し, 写しが写し先の外に出ないことを確かめる. `attach_data` は入れるたびに写し先の中の別のサブディレクトリに写す (入れ直したファイルが読めなくても今の写しが残る). 同じ元のファイル (`data.origin` が同じ) で大きさと更新の時刻 (ナノ秒) が変わっていなければ今の写しを使う. 古い写しは `prune_copies(写し先, 今の場所)` で片付ける (画面は保存の後に呼ぶ). 写す前に空きを確かめ, 一時の名前に写してから置き換え, 失敗したら一時の写しを消す. ディレクトリの中のリンクは指す先を写す (元から独立). 古い写しの片付けは attach_data が作った名前 (12 桁の 16 進) のサブディレクトリだけで, 写し先に置いた他のファイルは消さない. 写し先そのものはデータにできない. 写し先の中のファイルを入れた場合, 元の場所は前と同じ場所のときだけ引き継ぐ. 読めなければ新しい写しを消す. 写しが消えた場合 (置き場の問題の設定を消したなど), 受け渡し, 分析, 骨組みは `data.origin` を使う (`data_location`)

### 今のやり方をデータで書く

指標の今の値に根拠を持たせるため, 今のやり方 (1 の「今はどうしていますか」) をデータの上で書き表す問い (`action.current`. 7 の損得と制約の後) を置く. 答えの形は種類ごと.

| 種類 (`type`) | 意味 | 使える行動の型 |
| --- | --- | --- |
| `lag` | k 期前の目的の値と同じ (例: 前の週の同じ曜日と同じ数. `periods: 7`) | 量を決める |
| `mean` | 直前の k 期の目的の値の平均 | 量を決める |
| `column` | データの列に今のやり方の値がある (量なら置いた量, 選ぶと振り分けなら行動したか) | 全て |

- k 期前と平均は, ML-EDA の時刻でずらす手順 (`lag` の `time` と `freq`) と同じ扱いで数える (1 期はデータの時刻の間隔. 休みで日が飛んでも暦の k 期前. 系列を分ける列があれば系列ごと). 時刻の列が無ければ求めず, 今のやり方の値の列で書くよう知らせる. 平均は窓に値が 1 つでもあれば求める (ML-EDA と同じ)
- 損得の値か今のやり方が欠けた行は除く. 行動したかの列は, 数は 0 より大きいか, 文字は yes や はい などで読み, 読めない値は除く
- `inspect_data` は, データの上で今のやり方の実際の損 (量と振り分け) を, 問題の設定の損得で求め, データの期間 (時刻の列があれば日数と 30 日あたり. 1 日に満たなければ 30 日あたりは出さない) とともに返す. 指標の単位がお金 (円) か, まだ書いていなければ, 指標の今の値の候補 (`issue.kpi.current`) にも出す. 対象を選ぶ行動の得は求めない (行動した行の結果は行動の後の値で, 行動しなかった場合が分からないため. 試して確かめる). 求められない場合は理由を知らせる

## 8. 後ろの段階との書き戻し

全体のシステムでは, データの分析の段階 (ML-Fathom) が問題の設定のデータを開くとき, 目的の列, タスク, 分割, 除く列を決めた状態で始め, そこで変えた選び方は問題の設定に書き戻す. つなぐための部品はこのライブラリに置き, ML-Fathom の「問題の設定から始める」が使う.

- `recipe_from(problem)` は, データの読み方 (場所, 読み込みの種類と設定, 時刻の列) と, ML-EDA のレシピの雛形を返す. 止まるのは骨組みを組めない確かめの `error` だけで (骨組みの書き出しと同じ. 11 節の「残っている直すところ」), 組める `error` は知らせ (`notes`) に出す (「それでも書き出す」で書き出したプロジェクトから, データの分析の段階へ進めるように). 雛形は, 受け渡しの値から, 目的の列, タスク, 除く列の `drop_columns` の手順, 時系列なら系列ごとの過去の値の手順 (`lags` は決める時点で分かる最も新しい期. 時刻の間隔 (`data.interval_seconds`. データを入れたときに求める) が分かれば `time` と `freq` で時刻でずらし, 分からなければ行でずらして知らせる), 分割 (時系列は時刻の順, 相手をまとめる列があれば相手ごと, 分類は層別, 他は無作為. 相手の列は時刻の順でも `split.column` に書く). 書き戻したレシピの `split.column` と `ml.group_column` が違えば, 書き戻しの食い違いと `recipe_from` の知らせに出す. 前処理の残りの手順 (欠損, ワンホット, 標準化など) はデータの分析の段階で足す. 書き戻したレシピがあれば (`data.recipe`), それを返す (往復で同じになる)
- `apply_recipe(problem, recipe)` は, データの分析の段階で決めたレシピを問題の設定に書き戻す. 自動で書き戻すのは目的の列とタスクだけ (新しい目的の列は列の使い方から外し, 元の目的の列は決め直すよう知らせる). 列の使い方は方針なので黙って変えない: 使ってはいけない列をレシピが使っていれば食い違い (`error`), 分からない列をレシピが使っていれば, 分かる列に移すかレシピで落とすかを利用者が選ぶ問い (`choices`) にする (自動にできない判断は選ばせる). レシピの過去の値が決める時点で分からない期から始まる場合と, 時系列の予測で分割が時刻の順でない場合も食い違い (`warning`). 目的の列を落とす手順は誤り. 目的の列を変えたレシピが前の目的の列を使っていれば, 分かる列にするか落とすかを選ぶ問いにする (黙って特徴にしない). 落とすと選んだ列は, 過去の値の手順の他の手順 (ワンホット, 欠損の埋めなど) の対象から外し (対象が無くなった手順は除く), レシピの最後の落とす手順で元の列を落とす (過去の値は決める時点で分かるので残す. 前の手順がその列を使っても失敗しないように). 前の目的の列の問いは落とすを先に出す (予測したい値そのものは, ふつう予測の時点で分からない). レシピそのものは `data.recipe` に持つ. 返すのは書き戻した問題の設定, 変えた点の文, 食い違い, 選ぶ問い
- `resolve_choice(problem, column, option)` は選ぶ問いに答える (`known` で分かる列に移す, `drop` で書き戻したレシピの落とす列に足す)

### ファイルの組の受け持ち (予測するで, 画像の領域と点群)

正解が表の列でないので, レシピの代わりに ML-EDA のファイルの組の書き出し (`export_image_masks`, `export_capture_clouds`) の設定を下書きし, 書き戻す. 設定の形は次のとおり (名前は ML-EDA の引数にそろえる).

| 鍵 | 中身 |
| --- | --- |
| `function` | `export_image_masks` (画像の領域) か `export_capture_clouds` (点群) |
| `inputs`, `targets` | 入力のディレクトリ (画像か撮影) と正解のディレクトリ (領域か点群). 分からなければ `None` |
| `split` | ML-EDA の `split` (`method` は `random`, `group`, `none`. `valid`, `test`, `seed`) |
| `groups` | 件の id からグループ (同じ物や現場) の辞書. 無ければ `None` |
| `origin` | 正解の出どころ (ML-EDA の `origin` の `type`, `name`, `settings`) |
| `options` | 書き出しの他の引数 (`classes`, `mask_suffix`, `cloud_units`, 中身の手順 `item_steps`). 無ければ空 |

中身の手順 (`options.item_steps`) は, 項目の名前から手順の並び (`{image: [{op: resize, width: 64, height: 64}]}` など. ML-EDA の `item_steps` と同じ形) の辞書. 渡すと ML-EDA は手順をかけたデータセットを版 3 で書く. 問題の設定に持つのは, データの分析の段階で選んだ手順を開き直したときに埋め, 問題の設定から同じデータセットを作り直せるようにするため. 項目の名前は書き出しごとに決まる (`export_image_masks` は `image`, `export_capture_clouds` は `capture` と `cloud`. 領域の手順は ML-EDA が画像の `resize` から決めるので渡せない). 手順の名前と引数は確かめない (ML-EDA が書き出すときに確かめる. 手順の登録簿を写して持つと, ML-EDA で手順を足したときに食い違うため). 空の辞書と, 手順の並びが空の項目は無いものとして落とす

- `recipe_from(problem)` は, ファイルの組の受け持ちでは `recipe` を `None` にし, 設定の下書きを `export` で返す (列の予測では `export` が `None`). 書き出しは正解の種類で決める. 入力と正解のディレクトリは入れたデータの場所から埋める. 場所が入力と正解の 2 つのディレクトリ (`images` と `masks`, `captures` と `clouds`. ML-EDA の合成の見本と同じ名前) を持てばその 2 つ, 場所がその入力の名前で隣に正解の名前のディレクトリがあればその 2 つ, 他は場所を入力にし, 正解は `None` (画面で選ぶ). データを入れていないか, 入れたものがファイルの組のデータセット (版 2 か版 3) なら 2 つとも `None` で, 知らせを出す. 中身の手順は下書きでは空 (データの分析の段階で選ぶ). 分割は受け渡しの値 (グループがあれば `group`, 無ければ `random`) で, 割合は列の予測と同じ (検証用とテスト用 15 %. 骨組みは検証用の分割が要り, テスト用があれば評価を残すため). 正解の出どころは, 正解の出どころ (`target.source`) が今の処理なら `process` と処理の名前と設定 (`{"note": ...}`), 他は `unknown` (ML-EDA の種類と 1 対 1 に当たらないため, 画面で選ぶ). 書き戻した設定があれば (`data.export`), それを返す (往復で同じになる). ただし書き戻した設定の書き出しが今の正解の種類に合わなければ使わず, 下書きを返して知らせる
- `apply_recipe(problem, recipe)` は, ファイルの組の受け持ちでは設定を受け取り, `data.export` に持つ. 問題の設定の他の答えは変えない (列の答えが無いため). 形の誤り (知らない鍵, 知らない書き出し, 辞書でない分割やグループ, 文字でないディレクトリ, 中身の手順の形 (辞書でない, 書き出しに無い項目の名前, 手順の並びが辞書の並びでない, `op` が文字でない)) は誤りで止める. 書き出しが正解の種類に合わなければ食い違い (`error`), 検証用の分割が無ければ (`method` が `none` か `valid` が 0) 食い違い (`warning`. 骨組みの学習が止まるため), 分割がグループごとでグループが無ければ食い違い (`error`). 選ぶ問いは出さない. 返す形は列の予測と同じ
- 書き戻した設定は, 受け渡しのデータの分析の値 (`split`, `groups`) と, 骨組みの README の書き出しの案内 (中身の手順も) に使う. 書き出したデータセットは, ML-Fathom がプロジェクトの記録の場所 (`project.dataset`. config の `data.dataset`) に書くので, 問題の設定のデータ (`data.source`) は変えない

## 9. 確かめ

`check(problem)` は確かめの一覧を返す. 項目の場所と, 重さと, 何をすればよいかの文を持つ.

- **形**: 手で書いたファイルで, 値の形が崩れている (並びでない受け持ち, 辞書でない受け持ち, 知らない受け持ち, 1 件の単位, 出力の形, 正解の出どころ, 正解の種類, 作り方, その他の指標の向き, 版 1 のファイルの 4 つ以外の指標, 知らない意思決定の型やタスクや指標, 文字列でないタスク, 目的の列, 時刻の列, 当たりのクラス, 指標, 列の名前の並びでない値, 辞書でない分解の行, 文字列でない使い道と後段と守る指標の名前, 知らない使い道, 文の並びでない制約, 辞書でない方策の守り, 真偽値でない方策か, ROS2 か, GPU か, 文字列でない守りの答えと環境の登録名, 文, 数か数の並びでない決めた行動, 知らない集め方, シミュレータ, 外れたときの動き) (`error`. この場合は他の確かめをしない)
- **受け持ちの数**: 受け持ちが 2 つ以上 (`error`. 今は 1 つだけ書ける. 形の誤りと同じく他の確かめをしない)
- **知らない版**: 版が 1 以上の整数でないか, 知っている版より新しい (`error`. 他の確かめをしない)
- **足りない答え**: 今の答えのもとで要る問いの空 (`error`). 機械学習を使わない場合は, 1 から 4 と, 使うかとその理由だけを要る
- **筋道**: 機械学習で手伝う手 (`decomposition` の `ml: true`) が無いのに `ml.use` が `true` (`warning`. 何を手伝うのかが分からない). 指標の今の値と目指す値の向きが `better` と逆 (`error`)
- **タスクと行動**: `quantity` は回帰か予測, `select` と `triage` は分類で `positive` が要る (`error`). 分類で `positive` が無く, 行動が `none` 以外 (`error`)
- **時刻**: `forecasting` で `time_column`, `available_lag`, `horizon` が無い (足りない答え). 時刻の列が目的の列か, 系列を分ける列か, 使わない列に入っている. `horizon` と `available_lag` が 1 以上の整数でない (`error`)
- **列の答え直し**: 目的の列, 時刻の列, 系列を分ける列, 使う列と使わない列が, 使えるデータの列に無い (`error`. 列を答え直した後の古い名前)
- **使ってよい列**: 目的の列が `known` に入っている (予測の時点で分かるなら予測は要らない. 時系列で過去の値を使う場合は, 過去の値の列は後でデータの分析の段階で作るので, 目的の列そのものは `known` に入れない) (`error`). `known` と `unknown` の重なり (`error`). `columns` にあるのに `known` にも `unknown` にも無い列 (`warning`. 使ってよいか決めていない)
- **今のやり方**: 選ぶと振り分けを k 期前か平均で書いた (`error`). 今のやり方の列を学習に使ってよい列にした (`warning`. 今のやり方の結果は予測の後に決まる). 量の型で今ある量があり, 今のやり方を列で書いた (`info`. 推論のたどり直しには渡さない)
- **損得**: 損得の値が有限の数でない (非数と無限大) か 0 以下 (今ある量は負. 効果は 0 から 1 の外. `uplift` の効果は -1 から 1 の外) (`error`). `uplift` で向きが無い, `uplift` でないのに向きがある, 知らない渡し方と向き (空は既定の `share`), 手で書いた型に無い項目 (`error`). 列の名前で書いた値が使えるデータの列に無い (`error`. あれば行ごとの値として読む `info`). 根拠 (`basis`) が空 (`warning`. 根拠の無い損得では, 意思決定はもっともらしいだけになる). 対象を選ぶ型の効果は仮定 (`info`. `uplift` では見積もりで, 行動を無作為に割り当てて試して確かめる)
- **受け持ちの答え**: 受け持ちに合わない出力の形と正解の種類 (`error`. 選択肢に無い値). 環境の登録名が Gymnasium の登録名の形でない (`error`). 分類で出力の形がクラスでない, 回帰と予測で出力の形がクラス (`warning`)
- **指標**: 最良を選ぶ指標が受け持ち, 正解の種類, タスクに合わない (`error`). その他の名前に英数字と `_`, `.`, `@`, `-` の他の文字がある (`error`). 指標と課題の指標のつながり (`link`) が空 (`warning`)
- **今のやり方での指標の値**: 数でない, 負, 正解率と IoU で 1 より大きい (`error`. 割合は 0 から 1 で書く. 85 % なら 0.85. 骨組みは組めるので, 「それでも書き出す」の対象)
- **確かめ方と運用**: 確かめ方が空 (`error`). 対象を選ぶ型をたどり直しだけで確かめる (`warning`. 行動の効果は試さないと分からない). 止める条件が空 (`warning`)
- **使い道**: 予測を決まりで自動に決めるのに意思決定が `none` (`warning`). 後段の仕組みか機械学習に渡すのに, 後段が求めるもの (`ml.downstream`) が空 (`warning`. 評価は後段の結果で見るため)
- **守る指標**: 手で書いた, 数でない守る線と知らない向き (`error`). 解けたと言える指標と同じ名前 (`warning`). 機械学習を使うのに, 守る指標の名前が成功の基準 (9) にも止める条件 (10) にも無い (`info`. 良くしたい数字だけを追わないように. 名前がそのまま入っているかで見るので, 言い換えると出る)
- **その他の筋道**: 目指す値が今の値と同じ (`warning`), 分解の全ての手が機械学習 (`info`. 機械学習を使わない手と比べられない), 使わないと決めたのに機械学習で手伝う手がある (`info`)

`handoff(problem)` は後ろの段階ごとの値を返す. 確かめに `error` があれば誤り.

| 段階 | 値 | 使い方 (今は利用者が各段階の画面で選ぶ) |
| --- | --- | --- |
| データの分析 (ML-EDA, ML-Fathom) | `target`, `task`, `time_column`, `series_by`, `split` (予測と, 分類と回帰で時刻の順で分ける列 (`ml.split_time_column`) があれば `time`, 相手をまとめる列があれば `group`, 分類は `stratified`, 他は `random`. レシピの下書きの分割と同じ. 時刻の列は `time_column` で渡し, 学習に使わない列にしてもよい), `group_column` (相手をまとめる列. 時刻の順でも渡し, ML-EDA が分割をまたぐ重なりを知らせる), `min_lag` (過去の値の列に使ってよい最も小さいずらし幅. 予測だけ), `known` (学習に使ってよい列), `drop` (`unknown` と `forbidden` の列と, 今のやり方の列 (`action.current` の `column`). 今のやり方は決めることの結果で予測の時点では分からず, 学習に入れると答えが漏れるため. 利用者が `known` に入れた場合は落とさず, 確かめが注意を出す) | 読み込みの日時の列 (`load_data` の `time_column`. 系列を分ける列が複数あると ML-EDA は日時の列を推定できない), レシピの目的の列, タスク, 分割, 除く列 |

| モデルの作成 (ML-ModelControl, ML-CreateArchitecture) | `task`, `outputs` (回帰と予測は 1, 分類はクラスの数. 分からなければ空), `role`, `target_kind` | 出力の大きさ |

ML-Provide は一式につないだ問題の設定から推論の既定値を読む |

- 読む側は, 知らない値 (`requires`, `policy`, `project` など) を無視してよい
- 受け持ちの答えは `part` (`role`, `unit`, `output`, `target_kind`, `target_source`, `target_process`, `method`) で渡す. 学習・評価とモデルの作成にも `role` と `target_kind` を入れる
- 列の予測でない受け持ち (予測するの点群など) は, データの分析の値を同じ名前の空 (`target`, `task`, `split` は `None`, 並びは空) にし, 意思決定は `None`, 結論は空, 何期先までは `None` で渡す. ただしファイルの組の受け持ち (予測するの画像の領域と点群) は, 分割 `split` (書き戻した書き出しの設定の `split.method`. 無ければ, グループがあれば `group`, 他は `random`) とグループ `groups` (書き戻した設定の件の id からグループ. 無ければ `None`) を渡す. 他の型のデータの分析と推論への受け渡しは TODO.md にある

## 11. 骨組み

`make_project(problem, path)` は ML-Found のプロジェクトの骨組みを書き出す. 骨組みを組めない確かめの `error` があれば誤り. 骨組みを組める `error` (問題の設定の確かめの一部と, 入れたデータの確かめ) は, 「それでも書き出す」と指定すれば (`accept_errors`) 書き出せる (下の「残っている直すところ」). 既にあるファイルは上書きしない (`overwrite=True` で上書き).

```
<プロジェクト>/
├── problem.yaml                # 問題の設定の写し (元の場所 origin を持つ)
├── README.md                   # 課題の要約と, 次にすること (データの分析, モデルの作成, 学習)
├── configs/
│   ├── default/train.yaml      # 要る機能 (requires), 指標から monitor と mode. データセットとモデルの定義の場所
│   └── experiment/train.yaml   # 空の差分
└── train.py                    # 学習のスクリプト
```

- **元の場所**: `make_project(problem, path, origin=...)` は, 元の問題の設定 (`problem.yaml` か, それを持つディレクトリ) の絶対パスを, プロジェクトの `problem.yaml` の `origin` に書く. 学習のスクリプトは実験のディレクトリにこの写しをそのまま写すので, 実験の写しからも元が分かる. `origin` を省くと, 渡した問題の設定の `origin` をそのまま残す (写しから書き出し直しても元を指す). 書き出すプロジェクトの `problem.yaml` そのものを元にするのは誤り (写しが自分を指すため). 画面 (ML-Pathfinder) は置き場の `problem.yaml` を渡す
- 学習のスクリプトは, ML-EDA のデータセット (`outputs/dataset`) を読み, ML-ModelControl の定義 (`models/model.yaml`) からモデルを組み立て, ML-Found で学習し, テスト用の分割で評価し, 今のやり方と比べ (下の「今のやり方との比べ」), ML-Inference の推論の一式を実験の中に作る (問題の設定の意思決定と結論を既定値にする)
- **モデルの定義の写し**: 学習のスクリプトは定義を自分で写さない. ML-Found の `start_experiment` が config の `model.spec` の定義を実験に `model_spec.yaml` として写し, 中身の sha256 を `source.yaml` に記録する (写す処理を 2 か所に持たないように). 学習のスクリプトは, 定義のファイルがあるか (列の予測は無ければ止まり, ファイルの組は仮のモデルで学習する) と, 定義に誤りが無いか (ML-ModelControl の `validate` の `error`. 誤りの文を並べて止まる) を `start_experiment` の前に確かめる (誤りの定義で, 学習しない実験の出力先が残らないように. 外部の重みのファイルが読めるかは組み立てるときに分かる). その後に `Experiment` の `model_spec_path` (写した場所) からモデルを組み立て, 推論の一式 (ML-Inference の `make_bundle`) にも同じ写しを渡す. 写しから組み立てるときは, 定義の中の相対の参照 (外部の重み `weights.path` など) の起点に, 写した元の定義のディレクトリ (`model_spec_source.parent`) を `build_model` の `base_dir` に渡す (ML-Found は定義のファイルだけを写し, 参照するファイルは写さないため). 学習を始めた後にプロジェクトの定義を書き換えても, 記録の sha256, 学習したモデル, 一式の定義の 3 つがそろうように. 写せなかった場合 (`model_spec_path` が `None`. 定義がリンク, プロジェクトの外, 大きすぎるなど. 理由は `source.yaml` の `model_spec` の `status`) は止めず, プロジェクトの定義から組み立てて一式にもそれを渡し, `train.log` に警告を 1 行書く (ML-Found の勧めの形. 写しが無いので記録に sha256 も無く, 食い違いは起きない. 定義を組み直す前の試しの学習を止めないため). 学習のスクリプトは ML-Found の `Experiment.model_spec_path` が要る
- **要る機能**: config の一番上の `requires` に, 学習のスクリプトが読み込むライブラリ (列の予測もファイルの組も `eda`, `modelcontrol`, `inference`. ファイルの組は定義が無いうちは仮のモデルで学習し `modelcontrol` と `inference` を読まないが, 定義を置けばすぐ使うので, 先に入れておく) と, 受け渡しの `requires` (問題の設定から要る機能) を書く. ML-Found は学習の前に確かめ, 足りなければ入れ方を示して止まる. ML-Dashboard は同じ名前でプロジェクトの環境を作る
- **プロジェクトの記録**: `record_project(problem, path)` は, 書き出したプロジェクトの config (`data.dataset` と `model.spec`) をプロジェクトのディレクトリから絶対パスにして, 問題の設定の `project` に入れて返す (元は変えない. 前の記録は置き換える). 場所を config から読むのは, train.py が読む場所と同じにするため. 画面 (ML-Pathfinder) は書き出しの後にこれを保存する. プロジェクトの中の `problem.yaml` の写しには記録を持たせない (プロジェクトを動かしても古い場所を指さないように. train.py はプロジェクトのディレクトリからの場所で読む)
- タスクごとの損失と指標: 分類は交差エントロピーと正解率 (正解率を監視するなら, 同じ値を損失で比べる `trainer.monitor_tiebreak: valid/loss`), 回帰と予測は目的の値を学習用の平均と標準偏差で標準化した二乗誤差と元の単位の平均絶対誤差 (RMSE なら元の単位の二乗誤差を監視し, テスト用の評価はエポック全体から RMSE を求める. ML-Found はバッチの平均で書ける指標だけを平均するため)
- 推論の一式の確かめが学習の記録と比べられるのは, 監視した指標が `accuracy` か `mae` (ファイルの組の骨組みは `iou` か `chamfer`) の場合だけ (ML-Inference の決まり). それ以外では比べない理由を記録に書く
- 答えの文字 (名前, 予測すること, 比べる相手) と値 (意思決定, 結論など) は, Python の式 (文字は JSON の文字列, 真偽値と `None` は Python の名前. 長い文字列は空白か句読点の後で折り返す) か 1 行のコメントとして埋め込む (改行や引用符でスクリプトが壊れず, JSON の `true` や `null` が名前の誤りにならないように). 実験の名前は目的の列とタスクから作り, 日本語の文字は残す
- 検証用の分割の無いデータセットは, 学習の前に止めて案内する (最も良いモデルを選べないため)
- **今のやり方との比べ**: 問題の設定に今のやり方をデータで書き (`action.current`. 上の「今のやり方をデータで書く」), データを入れていれば, 学習のスクリプトは推論の一式を作る前に (一式づくりで止まっても比べの表が残るように), 検証用とテスト用で, 学習したモデルと今のやり方を同じ行で比べ, ML-Found の評価の表 (`evaluations/baseline_valid.json`, `baseline_test.json`) に推奨の形 (1 行に `rows`, `split_rows`, `<指標>`, `<指標>_baseline`, `<指標>_diff`. `baseline` に比べる相手の名前) で書く. 指標は回帰と予測では最良を選ぶ指標 (平均絶対誤差か RMSE), 分類では正解率
    - 今のやり方の値は, プロジェクトに写した元のデータ (`data/`) を問題の設定の読み方で読み, 元のデータの上で作る. 列はその値, k 期前と平均は ML-EDA の過去の値の手順を時刻でずらす扱い (データの候補の今のやり方の損と同じ). 分類は, 当たりのクラスに回したか (行動したか) の列から, 回した行は当たりのクラス, 回さなかった行はもう 1 つのクラスとし, 2 クラスで当たりのクラス (`positive`) がある場合だけ比べる
    - データセットの行と元のデータの行は, 元のデータにデータセットの前処理 (`Dataset.transform`) をかけ, 学習に使う列と目的の値 (と, データセットに残っていれば時刻の列. 数にして 6 桁に丸める) がそろう行を同じ行とみなしてつなぐ. ML-EDA のデータセットは元の行の位置を持たないため. 同じ値の行で今のやり方が違う行と, 見つからない行は比べず, 比べた行の数 (`rows`) と分割の行の数 (`split_rows`) を表に書く. 学習に使う列が無いデータセット (画像, 文, 点群の列) は, 目的の値だけでつなぐと値で行を選ぶことになるので比べない. 比べられないとき (元のデータが読めない, 前処理に要る列が無い, 目的の列が違うなど) は `train.log` に理由を書くだけで止まらない (続けて推論の一式を作る)
    - 表の説明には今のやり方の書き方 (`action.current`) も書く. 比べる相手の名前 (`ml.baseline` の文) と食い違っても, 何と比べたかが分かるように
    - 入れたデータが画像か文なら, 同じ行では比べず, 答えた今のやり方での指標の値 (`evaluation.current`. 5 節の「最良を選ぶ指標」) と比べる. 学習のスクリプトはテスト用の評価で, テスト用の分割のモデルの値 (分類は正解率, 回帰と予測は最良を選ぶ指標) と答えた値を並べ, ML-Found の評価の表 (`evaluations/baseline_test.json`. 1 行に `<指標>`, `<指標>_baseline`, `<指標>_diff`. `baseline` に比べる相手の名前) に書く. 表の説明, `train.log`, README に指標の画面の名前 (正解率など) と数え方と単位と, 「別のデータで数えた値との比べで目安です」を添える (今のやり方の値は利用者が他の件で数えた値で, テスト用の分割の件とは違うため). 表の説明には差 (`<指標>_diff`) がモデル − 今のやり方であることと指標の向きも書き, 相手の呼び方は, 比べる相手の名前が既定の「今のやり方」なら名前を括弧で繰り返さない. 答えた値が確かめで誤り (有限でない数, 負, 割合の指標で 1 を超える) なら答えていない扱いにし, 並べない理由 (値の誤り) をコメント, README, `train.log` に書く. 検証用では並べない (最良を選ぶのに使った分割なので). テスト用の分割が無ければ並べず, `train.log` に評価しないことと 1 行で書く
    - 比べられない場合 (入れたデータが画像か文で今のやり方での指標の値を答えていない, 今のやり方をデータで書いていない, データを入れていない, k 期前と平均で時刻の列か間隔が分からない, 分類で当たりのクラスか列で書いた今のやり方が無い. この順に 1 つ目の理由) は, 学習のスクリプトに理由を 1 行のコメントで書き (答えて書き出し直せば比べることも), README にも理由を書く. 印 (`TODO`) は残さない

    - 組めないもの: 受け渡しの値の形か, 学習のスクリプトの組み立てに使う答えの誤り (受け持ち, 目的の列, タスク, 時刻, 列の使い方, 今のやり方をデータで書いたもの, 指標, 方策の守り, 環境の登録名, 要る機能, データ. 版の誤り, 形の崩れ, 受け持ちの数の誤りは全て). 骨組みを組めない (組んでも動かない値をスクリプトや config に書く) ので, 指定しても書き出さない. 機械学習を使うかに答えていなければ「『機械学習を使いますか』に答えてください」で止める
    - 組めるもの: 項目の場所が, 課題 (`issue`), 分解, 決めることの文 (`action.who`, `when`, `what`, `basis`), 損得と制約 (`action.decision`), 確かめ方 (`verification`), 運用 (`operation`), 機械学習の仕組みの制約, 受け持ちの文の答え (何を出すか, 1 件, 比べる相手の名前, 使い道, 後段, 指標と課題の指標のつながり), 今のやり方での指標の値 (`evaluation.current`. 並べる値が外れるだけ) と同じ場所か, その下の項目のもの (`EXPORTABLE_ERRORS`. 頭の文字だけでは合わせない). 損得と制約の他は README の要約の文にしか使わないため. 問いと確かめの全ての項目の場所を, どちらに分けるかテストで決めておく (新しい場所はテストに足さないと落ちる)
    - 損得と制約の `error` (問題の設定の確かめと, 入れたデータの確かめの 2 クラスでない目的の列) が残るときは, 骨組みに渡す推論の意思決定 (`inference.decision`) を `None` にし, 学習のスクリプトは意思決定の既定値を付けずに推論の一式を作る (崩れた値を書くと, スクリプトの読み込みか学習の後の一式づくりで止まるため). README の一覧と `train.log` にそう書く. このとき骨組みの意思決定は `handoff` の値と違う
    - `open_errors(problem, inspected=None)` は, 組める `error` と, 入れたデータの確かめ (`inspect_data` の返す辞書の `findings`) の `error` を, `check` と同じ形の並びで返す. 画面が覚えておいた `inspect_data` の結果を `inspected` に渡せば, 重い分析をし直さない. ただし結果の印 (`key`. 下) が今の問題の設定とデータのものと違うか, 辞書でないか, `findings` が辞書の並びでなければ求め直す (古いか別の問題の設定の結果を信じないように). データを入れていなければデータの分は空. ML-EDA が無くてデータを読めない場合も, 確かめられていないので入る (文に「ML-EDA を入れると消える」と書く)

README の文と書き出せることは ML-EDA だけで見て, 学習と一式は ML-Found, ML-ModelControl, ML-Inference と PyTorch が入っている場合に動かす (CI の `train` のジョブ. 下の「ファイルの組の骨組み」の最後と同じ)
- 表と時系列の骨組みが学習から推論の一式まで通るかは, 自動のテストでは見ない. 骨組みを変えたら, 合成のデータで予測 (量を決める. 今のやり方は k 期前), 回帰 (今のやり方は列. RMSE を監視), 分類 (対象を選ぶ. 今のやり方は回したかの列) の骨組みに, `record_project` の場所へデータセットの書き出しとモデルの定義を置き, 学習から推論の一式まで通るか, 一式の確かめが学習の記録と合うか, 検証用とテスト用の比べる相手の評価の表が全ての行で書かれるかを確かめる
- 書く前に, 既にあるファイル (上書きしない場合) と, ディレクトリを作れない場所 (同じ名前のファイルがある, など) を全て確かめ, 1 つでもあれば何も書かずに誤りにする
- 骨組みは出発点で, 利用者が書き足す. 書き出した後の問題の設定の変更は, 骨組みには自動で反映しない (書き出し直すか手で直す)

### ファイルの組の骨組み (予測するで, 画像の領域と点群)

予測するで正解の種類が画像の領域 (`mask`) か点群 (`point_cloud`) の受け持ちは, ML-EDA のファイルの組のデータセット (版 2 か版 3. `export_image_masks`, `export_capture_clouds`) で学習する骨組みを書き出す. 領域は画像と領域の対から小さなモデルで領域の分割を学び, 点群は多視点の撮影 (画像, 姿勢, 深度) と正確な点群の対から, 深度から戻した点で物の表面の点群を予測する (Chamfer 距離を数エポックおきに検証). ファイルの並びは列の予測と同じ (`problem.yaml`, `README.md`, `configs/`, `train.py`).

- **データ**: 入れたデータがファイルの組のデータセット (版 2 か版 3) なら, プロジェクトの `data/` に写し, config の `data.dataset` をその場所にする (データの分析は済んでいる). README には版と, 版 3 なら項目ごとの中身の手順を書く (推論でも新しい 1 件に同じ手順をかけるため). データを入れていないか, 入れたものがファイルの組のデータセットでない (場所だけを答えた元の画像のディレクトリなど. `attach_data` は ML-EDA が読めるものだけを入れる) なら, `outputs/dataset` にし, README で ML-EDA の書き出しの関数と引数 (正解の出どころ `origin` を含む) を案内する (入れたものは列の予測と同じく `data/` に写す). 書き出しの設定を書き戻していれば (`data.export`), 案内にその引数 (ディレクトリ, 分割, グループの数, 中身の手順) を添え, ML-Fathom の「問題の設定から始める」で書き出せば `outputs/dataset` に入ることを書く
- **学習のスクリプト**: `load_items(...).split(...)` を torch の `Dataset` に包み (領域は値からクラスの番号の表で番号に. 名前の無い値 0 は背景 (`background`) のクラスとして足す (除くと正解が全て対象の外になり, 損失 0, IoU 1 の見かけだけの学習になるため. README にも書く). 他の名前の無い値と負の値は損失と IoU から除き, `train.log` に警告を出す. クラスが 2 つ未満なら止める. 撮影は深度から世界の座標の点に戻し (深度の大きさが画像と違えばカメラの内部の値を縮める), 決まった数を選ぶ. 学習用は読むたびに選び直し (torch の乱数から. 実験の種で同じ並び), 検証用とテスト用は件ごとに決まった選び), ML-Found の `Trainer` を継承して損失と指標を書く. 検証用の分割が無ければ学習の前に止めて案内する. テスト用の分割があれば, 学習した後の重みの指標を `save_evaluation` で `evaluations/` に残す (評価のエポックと説明は, 最良のモデルに戻した場合 (`trainer.final_weights` が `best`) だけ最良のエポック, 他 (`select_best: false` など) は最後のエポック). 比べる相手は, ファイルの組の受け持ちに今のやり方をデータで書く問いが無いので, 今のやり方での指標の値 (`evaluation.current`) を答えていれば, テスト用の評価の後に, テスト用の値 (`iou` は背景を除く平均, `chamfer`) と並べて列の予測と同じ形の評価の表 (`evaluations/baseline_test.json`. 「別のデータで数えた値との比べで目安です」を添える) に書き, README にも書く. 答えていなければ, その旨と, 8 の問いの題に答えて書き出し直せば並べること (指標が `loss` なら `iou` (領域) か `chamfer` (点群) を選ぶことも) を, コメント, README, `train.log` に書く. テスト用の分割が無ければ, 評価しないことと並べないことを `train.log` に 1 行で書く. 答えた値に誤りがあれば, 列の予測の画像と文と同じく答えていない扱いにする
- **モデル**: config の `model.spec` は列の予測と同じ `models/model.yaml` (ML-ModelControl の定義の場所) にする. `record_project` がこの場所を `project.model_spec` に記録するので, ML-CreateArchitecture は問題の設定を一覧から選んでそこに保存でき, ML-Dashboard の起動にも場所を打たずに済む. `train.py` はその場所にファイルがあれば ML-ModelControl で組み立て, 無ければ (場所を空にした場合も) 仮のモデル (`PlaceholderModel`. 動く小さなモデル) で学習し, `train.log` にその旨を書く (定義を組む前でも学習を確かめられるように. 置いたかどうかはファイルがあるかで決め, config は書き換えない). config の `model.placeholder: true` は, このように定義のファイルが無くても仮のモデルで学習できることの目印で, ML-Dashboard の学習の準備はこれがあれば定義が無いことを知らせにとどめ, 準備ができていないとはしない (`train.py` 自身は読まない. ML-Found はプロジェクト固有の項目として読まずに通す). 列の予測の骨組みは定義が無いと止まるので書かない. 仮のモデルには, 課題に合うモデルに置き換える印 (`TODO`) を付ける. 定義があれば, 列の予測と同じく ML-Found が実験に写したものから組み立て, 推論の一式にも渡す (11 節の「モデルの定義の写し」. 写せなかったときもプロジェクトの定義で学習する)
- **画像の領域**: 損失は画素ごとの交差エントロピー. 指標 `iou` は, エポック全体の重なりと和の画素数から求めた, 背景 (値 0) を除くクラスの IoU の平均 (`on_epoch_end` で全ての段階に記録. 最良を選ぶのは検証の `valid/iou`). クラスの名前は `dataset.yaml` の `classes`, 無ければ `values` (どちらも無ければ止めて案内). 予測にも正解にも無いクラス (空と空) の IoU は 1 (当てるものが無く, 外してもいない. 監視する指標が nan だと ML-Found が止まるためでもある). 検証用の分割の正解に背景しか無ければ `train.log` に警告を出す
- **点群**: 損失は 2 乗の距離の Chamfer (PyTorch だけで書く). 指標 `chamfer` (距離の Chamfer. 単位はデータセットのまま) は重いので, 検証したエポックの検証の段階だけで, バッチごとに求めて返す (ML-Found が件数の重みで平均する. 予測を貯めないので, 件数が多くても記憶が増えない) (`trainer.valid_every_n_epochs: 2`. ML-Found は検証しないエポックの記録に `valid/` を書かず, 最良, 打ち切り, 学習率の調整を検証したエポックだけで判定する. 打ち切りの待つ回数は検証の回数). 入力は撮影 (`capture`. OpenGL の軸, 深度は `z` だけ) か点群 (`point_cloud`)
- **実験の名前**: config には JSON の文字列 (引用符付き) で書く (`null`, `true`, `123` のような名前も文字のまま読めるように. 列の予測も同じ)
- **監視**: config の `trainer.monitor` と `trainer.mode` は受け渡しの値 (`valid/iou` と `max`, `valid/chamfer` と `min`, `valid/loss` と `min`)
- **task.yaml**: ML-Found の `task_from_dataset` でデータセットから受け持ち, 正解の種類と出どころを埋め, 問題の設定の出力の形 (`output`), 何を出すか (`what`), 作り方 (`method`) を足して `write_task` で書く. 元にした実験か重み (`base`) は印を残す
- **正解の出どころ**: README に書く. 正解の出どころが今の処理 (`process`) なら, 「指標はその処理との一致で, モデルはその処理を超えられない」と書き, 書き出しで `origin` に処理の名前と設定を渡すよう案内する (ML-EDA の `settings` は辞書なので, 問題の設定の文は `{"note": ...}` にして渡す). 入れたデータセットの `target.origin` も添える
- **見本**: 学習とテスト用の評価の後に, 検証用の分割の先頭の数件 (`SAMPLES`. 既定 3) の入力, 予測, 正解を ML-Found の `save_sample` で `samples/` に書く (学習の後なのでエポックは null. 名前は `valid_<番号>_input`, `valid_<番号>_predicted`, `valid_<番号>_target`. 説明に件の `id`). ML-Dashboard の見本のタブで見るため. 領域は入力を `image`, 予測と正解を `mask` にし, 予測のクラスの番号は領域の値に戻して, 正解はデータセットの値のまま書く (どちらもデータセットと推論の出力と同じ値). `classes` は値から名前の表 (名前の無い値 0 の `background` を含む). 点群は入力の点, 予測, 正解を検証と同じ選びの点で `point_cloud` にし, `convention` に単位 (`normalization.units`, 無ければ正解の項目の `units`) と, 正規化したデータセットなら件の `shift` (件の表の `normalization.columns` の値を ML-EDA の向きのまま. 見本の一覧の版 2 と同じ向きなので, ML-Dashboard が元の座標に戻せる) を書く. 書けない場合 (領域の値が 255 を超えるなど) は `train.log` に警告を出し, 学習の結果と推論の一式は残す
- **推論**: `model.spec` の場所に ML-ModelControl の定義がある場合, 学習とテスト用の評価の後に, 実験の中の `inference/` に ML-Inference の推論の一式を `make_bundle` で作り (名前は実験の名前), 一式の確かめを `train.log` に書く. 1 件の扱い (`items`) は学習と同じものを渡す. 領域は入力と正解の項目の名前と, クラスの番号ごとの領域の値 (値の番号の表から), 点群はそれに加えて選ぶ点の数 (`data.input_points`, `data.target_points`) と検証用の分割の乱数の種 (`data.seed` + 1). 検証用の分割と同じ点を選ぶので, 一式の確かめ (`valid/iou`, `valid/chamfer`) が学習の記録と合う. 仮のモデル (`PlaceholderModel`) は定義が無く一式にできないので, 作らない理由を `train.log` に書く. README には, 一式を ML-Provide で登録すること, 新しい画像や撮影を推論すると領域の値か元の座標の点群が返ること, 仮のモデルでは一式を作らないことを書く
- 合成のデータ (`ml_eda.synthetic`) から書き出した 2 つの版 2 のデータセットと, 中身の手順をかけた 2 つの版 3 のデータセットで, 骨組みを書き出し, スクリプトが Python として読めることをテストで確かめる. ML-Found と PyTorch が入っていれば 2 エポック学習まで通し, 学習の後の見本 (一覧の版 2, 領域の値の名前の表, 点群の `shift`) も見る. ML-Inference も入っていれば, `models/model.yaml` にモデルの定義を置いた骨組みで推論の一式まで作って確かめが学習の記録と合うかを見る (入っていなければ飛ばす). CI の `train` のジョブは CPU の PyTorch と ML-Found, ML-ModelControl, ML-Inference の main を入れてこれらを動かし, 飛ばしたテストがあれば誤りにする (他のジョブは入れないので飛ばす. 入れ忘れで黙って飛ばさないため). 骨組みを変えたら, 合成のデータで ML-ModelControl の同梱の例 (`unet_segmentation` のクラスの数を合わせたもの, `point_cloud_predictor`) を `record_project` の `model_spec` に置き, 学習, 見本, 推論の一式まで通るかと, 点群の見本を元の座標に戻すと元の点群に重なるかを確かめる

## 12. 書き出し

- `save_problem(problem, path)` は `updated_at` を今にして YAML で書く (一時ファイルに書いてから置き換える)
- `load_problem(path)` は読んで版を確かめ (版の無いファイルと, 知っている版より新しい版は誤り), 版 1 なら版 2 に移して返す

## 13. 安全

- 問題の設定 (`problem.yaml`) は `yaml.safe_load` で読む. ネットワークは使わない
- 手元のデータの写し先 (`attach_data` の `copy_to`) は絶対パスだけ. 元のディレクトリの中には写さない. 空きを確かめ, 一時の名前に写してから置き換える (途中で失敗しても前の写しが残る. リンクは指す先を写す)
- 写しの片付け (`prune_copies`) は, `attach_data` が作った写しのディレクトリ (12 桁の 16 進の名前) だけを消す. 他のファイルとリンクの指す先は消さない
- 骨組みの書き出し (`make_project`) は, 既にあるファイルを `overwrite` 無しでは上書きしない. 全てを確かめてから書く (途中で止まって一部だけが残らないように)
- 骨組みの書き出しは, 骨組みを組める確かめの `error` が残っていれば, 「それでも書き出す」と指定しなければ (`accept_errors`) 書かない. 指定して書いた場合は README に一覧を残す. 骨組みを組めない `error` があれば, 指定しても書かない
- 指標の名前は英数字と `_ . @ -` だけ (学習の記録と曲線のファイルの名前になるため. `.` と `..` は誤り)

## 14. 課題の型への広げ方

機械学習の課題は, 1 件の分からない値を当てる「予測する」(分類, 回帰, 時系列の予測. 検出, 領域分け, 文字起こし, 3D の形のような構造のある出力と, 正解のほぼ無い異常の検知も) のほかに, 正解が 1 つに決まらない中身を「作る」, 多くの候補から「並べる」(推薦, 検索), 正解の無いデータを「まとめる」(群分け), 行動の「効果を見積もる」(uplift, バンディットや強化学習の方策) に分けられる. 正解の出どころ (列, 対のファイル, 自分自身, 今の処理の出力, 行動の結果, 介入の記録, 指示 (プロンプト)), 1 件の単位 (行, まとまり, 対, 要求と候補, 窓), 作り方 (規則, 既製のモデルをそのまま, 頭だけ学習, 微調整, 一から) で, データの形と確かめ方が変わる. 広げる順は, 約束 (ファイルの形の版) を変えずに出せるもの → 約束の版を上げるもの → 型ごとの通り道.

- 受け持ちは, 課題から見た機械学習の最後の出力に付ける 5 つ (予測する, 作る, 並べる, まとめる, 効果を見積もる). 今の時間のかかる処理を速くする「置き換え」は受け持ちにせず, 正解の出どころ (今の処理の出力), 守る指標 (今と同じ結果), 元に戻す道で書く. 埋め込み (表す) は段の部品で, 受け持ちにしない
- 1 つのファイルに課題は 1 つ. 受け持ちは並びで持つ (今は 1 つだけ許す. 守る指標と確かめ方は課題に 1 つ)
- 版 2 は, 型に依らない 5 つの問いと, 受け持ちと正解の種類ごとの指標の候補を持つ (上の「受け持ちと, 型に依らない 5 つの問い」). 並べる, まとめる, 効果を見積もるの続く問いは最小限. 骨組みを書き出せるのは, 列の予測と, 予測するの画像の領域と点群
